# POS → Inventory sales and refund events

POS sends stock changes to the Inventory system's REST API. Inventory provides the receiving endpoint; POS does not require an incoming API for this delivery direction.

## Receiver

`POST http://10.36.189.247/inventory-laravel/public/api/v1/pos/stock-events`

Headers:

```http
Authorization: Bearer <Inventory receiver token>
Accept: application/json
Content-Type: application/json
```

Keep the receiver token private. POS reads it from `INVENTORY_API_TOKEN` in `.env`.

Request example (the event key is generated by POS, not manually invented):

```json
{
  "event_key": "<POS_INSTANCE_ID>:<outbox_event_id>",
  "sku": "BEV-3411",
  "event_type": "sale.completed",
  "quantity_delta": -1
}
```

Sales use `sale.completed` and a negative quantity. Restocked refunds use `sale.refunded` and a positive quantity. Quantities support three decimal places. Events identify products by Inventory SKU, not the POS integer product ID. Monetary refunds without restocking must not increase Inventory stock.

Successful response:

```json
{"accepted": true, "duplicate": false}
```

The receiver must apply stock changes transactionally and store event keys. Repeating the same key/payload acknowledges success with `duplicate: true` without applying stock twice. Reusing a key with another payload returns HTTP 409. Invalid events or insufficient stock must reject the event without changing stock.

## Automatic delivery

POS queues the event in the same database transaction as the sale/refund. `php artisan schedule:work` runs `integrations:sync` every minute. `php artisan integrations:sync inventory` can trigger delivery immediately. POS marks events processed only after an accepted acknowledgement; failures remain queued for retry using the same event key.

## Verified live

On 2026-10-10, POS sale 1 produced event 1 for SKU `BEV-3411` with quantity delta `-1`. Inventory acknowledged it, and POS marked it processed. An authenticated catalog lookup then returned on-hand stock 99, matching POS stock 99. This verifies the live sale-delivery path. Refund delivery uses the same REST contract and has automated regression coverage; a live customer refund was not fabricated for testing.
